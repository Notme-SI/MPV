# Оформление выпусков

Описание каждого выпуска хранится в `releases/<версия>/README.md` и копируется в описание соответствующего GitHub Release. Файлы в репозитории и текст на странице Releases — разные записи: изменение Markdown-файла само по себе не меняет опубликованное описание.

Используйте оформление существующих выпусков:

1. Раздел `### Windows` с изменениями именно этой версии. Каждый пункт начинается с значка и короткого выделенного типа: «Исправления», «Интерфейс», «Обновления» и т. п.
2. Раздел `### 📚 Документация` со ссылками на руководство, историю и лицензии.
3. Значок версии выпуска. Используйте обычный значок Shields, которому не требуется запрос к GitHub API.
4. Раздел `### 📥 Скачать` с таблицей Windows x64 и отдельными кнопками Setup / Portable, ведущими на реальные файлы выпуска.
5. Краткие указания по запуску и контрольным суммам. Имена исполняемых файлов должны соответствовать описываемой версии.

Загружайте ZIP и установщик до публикации выпуска. Кнопки используют точные имена файлов из GitHub Releases; встроенные архивы Source code не заменяют готовую сборку.

## Автоматическое обновление README

Workflow [Update release downloads](../.github/workflows/release-docs.yml) запускается при публикации или редактировании релиза, а также вручную через Actions → Update release downloads → Run workflow. Он запрашивает последний стабильный выпуск, проверяет наличие обоих загруженных файлов и обновляет только блок между комментариями `release-downloads:start` и `release-downloads:end` в README основной ветки `main`.

Генератор: [`tools/update-release-docs.cjs`](../tools/update-release-docs.cjs). Он подставляет номер версии и прямые ссылки автоматически. Общую документацию, исходники, теги и файлы релизов workflow не меняет. Если ZIP или установщик ещё не загружен, workflow завершится ошибкой и оставит прежние ссылки; после загрузки запустите его повторно. Для нового релиза также заранее добавьте `releases/<версия>/SHA256SUMS.txt`, на который ссылается блок загрузок.

Workflow требует разрешения `contents: write` для встроенного `GITHUB_TOKEN`. Если запись в `main` ограничена правилами репозитория, примените сгенерированный блок через обычный PR. При недоступности сервиса значков текстовые подписи ссылок остаются в Markdown как alt-текст.
